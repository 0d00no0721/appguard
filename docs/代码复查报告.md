## 3. 逐条确认过的"看起来像问题、实际正确"

| 项 | 结论 |
|---|---|
| `from __future__ import annotations` 被判"未使用" | 编译指令，**工具已加白名单** |
| `ast.NodeVisitor.visit_*` 被判死代码 | 框架回调，**工具已加白名单** |
| `except KeyboardInterrupt: pass`（cli.py） | Ctrl+C 是 `serve` 的正常退出路径 |
| `winapi.py` 里 20+ 处 `except: pass/continue` | 全是"尽力而为"的枚举（`OpenProcess` 被拒、注册表键不存在、句柄关闭失败…）；模块 docstring 已声明"任一进程取不到信息都不能让整轮采集失败"。**保留** |
| `audit` 解析坏行时 `continue` | 日志可能被外部截断；跳过坏行继续读是对的。**保留** |
| `_in_use_of` 时间戳解析失败即跳过 | 主判据是窗口/前台，时间戳只是"刚启动"的补强；跳过方向**偏保守**（宁可不判在用）。已在注释写明 |

## 5. 仍未解决的已知边界（诚实清单）

1. **真机"见即杀"未做端到端验证**：需要管理员权限 + 等雷电服务定时器真实触发。本轮只验证了"计划生成 + dry-run 执行"；真实结束进程只在受控的 `tools/smoke_kill.py`（自起进程 + PID 复用防护）里验证过。
2. **非管理员下有 16~28 个系统进程取不到 exe**，被合并进「系统组件（路径不可读）」组 ⇒ 分类覆盖率 91% 而非 100%。这是权限上限，不是 bug。
3. **`cleanup.execute` 的并发保护是"整段加锁"**：执行期间其它写操作会排队（`E_BUSY` 只在跨进程竞争时才可能返回，进程内是阻塞）。当前规模够用，未做细粒度锁。
4. **`hook` 式的 `bus._deliver` 覆写**（PipeServer/TcpServer 构造时替换 EventBus 的投递方法）：两个服务端同时存在时后者会覆盖前者。当前实现二选一，`auto` 模式下先行者失败才启用后者，因此不会同时存在——但这是个**隐式约束**，若将来做双通道并行需要重构。
5. 静态工具是自研的，对 `getattr(obj, "name")` 形式的动态引用会误报（当前已加 visit_*/__future__/run/main 白名单）。
